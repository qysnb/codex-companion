# 0.4.2：修复正常慢响应被过早取消

根因：传输层和额度服务层分别写死了10秒截止时间。本机只读对照观察到合法额度响应耗时约16.3秒，另有账户初始化耗时超过10秒。旧版会在有效响应到达前取消并丢弃连接，随后重启又触发冷初始化，表现为频繁“读取超时”。这说明普通网络可用不等于该接口一定会在10秒内完成。

修复：账户 `account/read` 和额度 `account/rateLimits/read` 统一使用30秒请求预算，由同一策略提供给两层，避免只改外层而仍被内层提前中止。初始化握手和其他请求保持10秒，提前响应立即完成，不增加固定等待。真实超过30秒仍按现有错误和退避策略处理。

缓存读取仍为即时内存访问。退出会立即取消待处理请求；不延长后台连接常驻时间，不改变刷新间隔、重置提醒、账户隔离、角色或其他偏好。

回归：旧实现先在10.5秒才返回有效账户响应的测试中失败；修复后账户和额度两个慢响应测试均通过，且验证没有重复请求、内存快照不阻塞、关闭及时释放。其余核心测试通过。真实链路连续三次独立冷启动均返回Live，整体约18.7／18.5／19.8秒，账户步骤均跨过原10秒边界。

边界：这项修复让正常慢响应有机会完成，不会把外部接口变成150ms服务，也不保证服务永远可用。150ms目标仍是已缓存数据的界面显示路径。
